# Demo Readiness Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Restore login on the VPS-hosted backend, ship a DB migration for two already-complete
features (funnel pages, WhatsApp templates) that are missing their table, fix three concrete
mobile-jank bugs on the marketing site, and verify all of it end-to-end before tomorrow's demo.

**Architecture:** No new feature code is needed for funnel pages or WhatsApp templates — both are
fully implemented already (entities, resolvers, services, controllers on the backend; pages,
forms, hooks on the frontend in `packages/asturian-front/src/modules/funnel/` and
`.../settings/accounts/*WhatsappTemplate*`). What's missing is the database migration that creates
their tables, and a working VPS backend to serve the schema at all (it's currently missing even
`getLoginTokenFromCredentials`, which has existed in the code since the initial commit — the VPS
is simply running stale/broken code). This plan: (1) generates the missing migration locally, (2)
writes a single self-verifying recovery script for the user to run once on the VPS, (3) fixes three
independent, code-level mobile performance/layout bugs in `zyra-website`, (4) wires up the funnel
page's env var and a demo row once the backend is healthy, (5) verifies everything end-to-end.

**Tech Stack:** NestJS + TypeORM + GraphQL (zyra-server), React 19 + Vite + Jotai (asturian-front),
Vite SSR-prerendered SPA (zyra-website), PM2 process manager on the VPS, Vercel CLI deploys.

## Global Constraints

- No new Vercel projects — deploys go to the two existing projects, `workshop-os` (website) and
  `workshop-os-app` (CRM front). Swap `vercel.json` via the established scratchpad-backup pattern
  before any `vercel deploy`.
- The VPS (`srv1938428`, `/root/zyra`) is only reachable through the user's own terminal. The
  recovery script (Task 2) must be self-contained and end with a single `PASS`/`FAIL` line — no
  multi-step back-and-forth.

  closest reference for a plain `WorkspaceRelatedEntity` with no relations;
  `WhatsappChannelEntity` for one with a `ManyToOne` relation.
- Every entity change needs an instance command migration
  (`npx nx run zyra-server:database:migrate:generate --name <name> --type fast`) — never hand-write
  migration SQL.
- Run `npx nx lint:diff-with-main` and `npx nx typecheck` on any package touched, before
  committing.

## Task 2: Write the VPS recovery script

**Context:** Direct probing (`curl` against `https://zyra-api.179-199-135-212.sslip.io/graphql`)
confirms the live backend's schema is missing `getLoginTokenFromCredentials`, which has existed in
`packages/zyra-server/src/engine/core-modules/auth/auth.resolver.ts` since the initial commit. A
prior rebuild+restart attempt (git pull, native-binding fix, `nx run zyra-server:build`, `pm2
restart`) did not fix it, which points at either a zombie process still holding port 3002, or the
Redis quota-exhaustion crash-loop (`ERR max requests limit exceeded`) preventing the app from ever
reaching a stable, fully-registered state. The user will run this script once and paste back only
its final line.

**Files:**
- Create: `scripts/vps-recover.sh`

**Interfaces:**
- Consumes: nothing from other tasks (runs against the VPS, independent of local code changes,
  though Task 1's migration must be committed and pushed before this script's `git pull` step picks
  it up)
- Produces: a `RECOVERY: PASS` or `RECOVERY: FAIL <reason>` line on stdout — this is what the user
  pastes back, and what Task 8/9 wait on before proceeding

- [ ] **Step 1: Write the script**

Create `scripts/vps-recover.sh`:

```bash
#!/bin/bash
# Run this ON THE VPS (as root, from anywhere) to recover the zyra-server
# backend into a known-good state: kills any stale process on :3002, pulls
# latest, rebuilds cleanly, applies pending DB migrations, restarts via pm2,
# and self-verifies the GraphQL schema is actually current before printing
# a single PASS/FAIL line.
set -uo pipefail

REPO_DIR="/root/zyra"
PORT=3002
FAIL() { echo "RECOVERY: FAIL - $1"; exit 1; }

echo "== 1/7: diagnosing current state =="
pm2 jlist 2>/dev/null | grep -q '"name":"zyra-server"' && echo "pm2 knows zyra-server" || echo "pm2 has no zyra-server entry yet"

echo "== 2/7: force-killing anything on :$PORT (pm2-tracked or not) =="
pm2 delete zyra-server zyra-worker >/dev/null 2>&1
fuser -k ${PORT}/tcp >/dev/null 2>&1
sleep 2
if ss -tlnp | grep -q ":$PORT"; then
  FAIL "something is still listening on :$PORT after kill — investigate manually with 'ss -tlnp | grep $PORT'"
fi
echo "port $PORT is free"

echo "== 3/7: git pull =="
cd "$REPO_DIR" || FAIL "repo dir $REPO_DIR not found"
git checkout -- package-lock.json 2>/dev/null
if ! git pull; then
  FAIL "git pull failed — check for local changes with 'git status' and resolve manually"
fi

echo "== 4/7: install (with devDependencies — NODE_ENV=production would skip them) =="
if ! npm install --legacy-peer-deps --include=dev; then
  FAIL "npm install failed"
fi

echo "== 5/7: build (with Linux native-binding workaround) =="
npm install --no-save --legacy-peer-deps --include=dev \
  @rolldown/binding-linux-x64-gnu @swc/core-linux-x64-gnu \
  @typescript/native-preview-linux-x64 >/dev/null 2>&1
npx nx reset >/dev/null 2>&1
if ! npx nx run zyra-server:build; then
  FAIL "build failed — re-run 'npx nx run zyra-server:build' manually to see the error"
fi

echo "== 6/7: apply pending DB migrations =="
if ! npx nx run zyra-server:database:migrate; then
  FAIL "database:migrate failed — check DB connectivity and the migration output above"
fi

echo "== 7/7: restart via pm2 and verify the schema is current =="
pm2 start packages/zyra-server/dist/main.js --name zyra-server --cwd packages/zyra-server
pm2 start packages/zyra-server/dist/main.js --name zyra-worker --cwd packages/zyra-server -- worker
pm2 save >/dev/null 2>&1

echo "waiting up to 60s for the server to come up..."
UP=0
for i in $(seq 1 12); do
  if curl -s -o /dev/null -w "%{http_code}" http://127.0.0.1:${PORT}/healthz | grep -q "200"; then
    UP=1
    break
  fi
  sleep 5
done
if [ "$UP" -ne 1 ]; then
  FAIL "server did not come up healthy within 60s — run 'pm2 logs zyra-server --lines 50 --nostream'"
fi

LOGIN_PROBE=$(curl -s -X POST http://127.0.0.1:${PORT}/graphql \
  -H "Content-Type: application/json" \
  -d '{"query":"mutation { getLoginTokenFromCredentials(email:\"probe@example.com\",password:\"x\",origin:\"x\") { loginToken { token } } }"}')

if echo "$LOGIN_PROBE" | grep -q "Cannot query field"; then
  FAIL "schema still missing getLoginTokenFromCredentials after a clean rebuild — this points at something deeper than a stale build; capture 'pm2 logs zyra-server --lines 100 --nostream' and share it"
fi

FUNNEL_PROBE=$(curl -s -X POST http://127.0.0.1:${PORT}/graphql \
  -H "Content-Type: application/json" \
  -d '{"query":"query { __type(name: \"FunnelPage\") { name } }"}')

if ! echo "$FUNNEL_PROBE" | grep -q '"name":"FunnelPage"'; then
  FAIL "schema is missing the FunnelPage type even after migrate — check 'npx nx run zyra-server:database:migrate' output above for errors"
fi

echo "RECOVERY: PASS"
```
